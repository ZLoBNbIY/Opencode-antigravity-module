# Маршрутизация Google: разбор Antigravity Unlocker

Исследованный репозиторий: https://github.com/confeden/Antigravity
Коммит: `b9678d4a884140982aa42284a882f84b3f0dd2bf`.

## Вывод

Unlocker сочетает патч официального клиента, локальный транспортный прокси и
выбор внешнего выхода. Подмена DNS направляет соединение к этому прокси; сама
по себе смена DNS не снимает серверные ограничения Google.

Для Hub нужен независимый менеджер маршрутов с проверкой реальной генерации.
Уже существующий `gui-manager/provider_proxy.py` реализует значительную часть
транспортного слоя. Для независимости от Unlocker необходим собственный
проверенный выход (например, VDS), а не только локальная реализация прокси.

| --- | --- | --- |

| CONNECT-прокси | Слушает `127.0.0.1:53129`, имеет резервные порты, переносит TLS как поток байтов | `src/proxy.rs` |

| Выходы | Пользовательский прокси, групповой прокси, встроенные выходы, relay, DNS-подставленный адрес, VPN | `src/routes.rs`, `src/upstream.rs`, `src/group.rs` |
| Выбор пути | Учитывает приоритет пользователя, успешные ответы модели, задержки и временное исключение неудачных путей; сбрасывает свидетельства при смене сети | `src/routes.rs` |

Текущий публичный транспорт не завершает клиентский TLS и не требует своего CA.
В коде осталась очистка сертификата от старых версий. Ошибки региона и ответы
модели он узнаёт из логов клиента, а не из расшифровки CONNECT-туннеля.

Комментарии разных версий местами описывают прежний порядок приоритетов.
В текущем `routes.rs` групповой и пользовательский прокси имеют особый приоритет,
с учётом того, какой был добавлен позже; далее учитываются результаты маршрутов.

## Что отсутствует в публичной сборке

`build.rs` условно подключает отсутствующие приватные `src/exits.rs`, `.exits`,
`src/relay.rs`, `.relay_key`. Старый relay выключен по умолчанию; для его включения
нужны приватные файлы и `AG_WITH_RELAY=1`. Клиент группового прокси опубликован,
но его серверная реализация и инфраструктура не включены в репозиторий.

Следовательно, сборка публичного исходника не воспроизводит весь набор выходов
официального бинарника. По одному успешному ответу через локальный Unlocker
нельзя установить, какой конкретно внешний выход обслужил запрос.

Лицензия нестандартная, ограничивает модификации и производные работы без
разрешения автора. Перенос исходников в Hub требует отдельного согласования;
предлагаемая интеграция должна опираться на собственную реализацию стандартных
DNS/HTTP CONNECT/TLS-механизмов.

## Подтверждённое локальное сравнение

Один активный аккаунт, модель `gemini-3.8-flash-high`, запрос `Reply with exactly: OK`:

1. Hub с маршрутом Google `proxy` через внешний HTTP-прокси:
   daily endpoint → `400 User location is not supported`; основной → `429`.
2. Без HTTP-прокси, через системный DNS и локальный Unlocker:
   daily endpoint → HTTP 200, текст `OK`, завершение `STOP`, 2,53 с.
3. После изменения маршрута Google в Hub на `direct`:
   через диспетчер Hub `127.0.0.1:10880` → HTTP 200, `OK`, `STOP`, 4,09 с.

Здесь `direct` означает отсутствие дополнительного HTTP-прокси Hub.
Системный DNS всё ещё направляет соединение в Unlocker: это не доказательство
прямого выхода к Google через провайдера и не независимость от стороннего ПО.

Первый пробный запрос с лимитом 64 токена завершился `MAX_TOKENS` без текста.
Повторный с лимитом 2048 дал `OK`. При проверке thinking-моделей маленький лимит
нельзя интерпретировать как недоступность модели.

## Архитектура для Hub

### 1. Явные маршруты и диагностика

Развить `provider_proxy.py`: несколько именованных маршрутов для Google,
отдельное состояние для каждого endpoint, отображение выбранного пути и причины
выбора. Сохранить существующие direct/VLESS/HTTP proxy/DNS-варианты.

Для совместимости с установленным Unlocker можно добавить явный CONNECT-выход
на его локальный порт, обнаруживая фактический порт, а не полагаясь только на
53129. Такой режим остаётся зависимым от сторонней программы.

### 2. Проверка на уровне API

Развить `health_checker.py`: короткий запрос генерации через конкретный маршрут,
проверка SSE, текста и причины завершения. Разделять:

- ошибку DNS/TCP/TLS/CONNECT;
- региональный `400` по конкретному сообщению;
- `401`/ошибку авторизации;
- `429`/квоту или перегрузку;
- `503`/мощности модели;
- HTTP 200 с ошибкой в SSE, пустым ответом или `MAX_TOKENS`;
- успешный ответ модели.

Список моделей, HTTP 404 корневого URL и успешный TLS handshake не являются
проверкой возможности генерации. HTTP 429 не доказывает неисправность маршрута.

### 3. Обратная связь и переключение

CONNECT-прокси не видит HTTP-ответы внутри TLS. Автоматическое переключение после
региональной ошибки нужно реализовать на уровне API-клиента либо через явный
локальный канал результатов от него к менеджеру маршрутов. Диагностический
пробник Hub может сообщать результат напрямую.

Сохранять route ID, endpoint, модель, время, код и категорию ошибки без токенов.
Выбирать подтверждённо рабочий путь, временно исключать неудачный, ограничивать
число повторов. Не повторять автоматически уже начавшую выдавать текст генерацию.
Учитывать reuse соединений: новый маршрут применяется к новым туннелям.

### 4. Собственный выход на VDS

На Linux достаточно аутентифицированного CONNECT-прокси или уже поддерживаемого
VLESS; установка IDE Antigravity для сетевого выхода не нужна. Ограничить
доступ своим клиентом и нужными направлениями. TLS к Google остаётся сквозным.

Перед выбором VDS как основного пути проверить генерацию тем же аккаунтом и
моделью. География IP сама по себе не гарантирует доступность, а сетевой выход
не создаёт квоты или доступ к недоступной аккаунту модели.

## Порядок реализации

1. Диагностика маршрута и достоверный тест генерации в Hub.
2. Настройка и проверка собственного VDS через существующий транспорт.
3. Менеджер Google-маршрутов с обратной связью, cooldown и отображением причин.
4. Подключение API-клиента к обратной связи для рабочих запросов, не только тестов.

Для запросов самого Hub системный DNS-сервис, NRPT и патч официальных бинарников
не обязательны: приложение уже контролирует собственный транспорт.

## Встроенный независимый транспорт Hub

Маршрут **Google SmartDNS (встроенный)** реализован в `google_smart_dns.py`.
Он заменяет первоначальную интеграцию с локальным Unlocker:

1. Hub запрашивает A-запись Cloud Code-домена по DoH/HTTP2.
2. Проверяет DNS transaction ID, вопрос, флаги, записи и публичность адреса.
3. Открывает TCP-соединение к полученному IP, передавая клиентский TLS без изменений.
4. Клиент проверяет сертификат исходного Google-домена обычным способом.

Для Cloud Code не используется системный резолвер, NRPT, `ag_dns.exe`,
`AG_LS_PROXY`, loopback-входы Unlocker или его CONNECT-порт. OAuth и остальные
Google-домены сохраняют общие настройки сети Hub. Ответы DoH кешируются с TTL
до 120 секунд; при ошибках соединения кеш сбрасывается. Несколько A-записей
пробуются при TCP-ошибке в пределах общего бюджета времени.

По умолчанию используется публичный `https://dns.dns-ai.ru/dns-query`.
Адрес меняется в разделе «Сеть», поле DoH для Google SmartDNS,
ключ конфигурации `google_smart_doh`. Требуется `httpx[http2]` из requirements.
HTTP_PROXY процесса не применяется к DoH-запросам, что исключает рекурсию.

Это независимость от стороннего приложения на ПК, а не от внешней инфраструктуры:
SmartDNS-сервис предоставляет адрес пересылки трафика. Для собственного выхода
можно использовать VDS с уже поддерживаемым VLESS/CONNECT. Квоты Google остаются.

### Проверка независимости

Реальный запрос через новую реализацию Hub дал `OK` от `gemini-3.8-flash-high`
за 3,327 с. Во время теста вызовы соединения с Cloud Code по имени, локальными
портами сторонних прокси и `127.65.71.*` были запрещены инструментированием.
Зафиксирован путь: клиент → временный CONNECT Hub → `dns.dns-ai.ru:443`
для разрешения имени и `193.233.112.88:443` для генерации. Адрес получен по DoH,
в код не зашит. Unlocker на машине установлен, но в этом пути не участвовал.

Кнопки **Диагностика маршрута Google** и **Тест Gemini 3.8** показывают
сохранённый маршрут, адреса SmartDNS и результат настоящей генерации.
Тест использует до 2048 выходных токенов и различает ошибки двух endpoint,
регион, квоту, авторизацию, пустой ответ и лимит теста.
